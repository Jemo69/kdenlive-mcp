Kdenlive
MCP Server

A Model Context Protocol server that drives the KDE video editor Kdenlive by editing its native MLT XML project file. No GUI scraping. No window automation. Deterministic, headless, identical on Linux, macOS, Windows and WSL.

Python 3.10+ FastMCP 4 uv managed 32 tools 81 tests green MIT

The short version

A .kdenlive project is an XML document. Upstream documents the format in dev-docs/fileformat.md, and every fact about a project — clips, tracks, effects, transitions, timing — is in that one file. So the MCP reads and writes that file directly instead of pretending to be a human with a mouse.

That single decision is what makes this work where the video-editor MCPs on the market do not. A GUI-scraping server needs a display, a specific window layout, and it loses races against the UI. This one needs nothing but Python. It works in CI, it works over SSH, it works while the editor is closed, and it produces the same bytes on every operating system.

Your questions, answered

Do users have to set environment variables and stuff like that?

No

Zero configuration is the default. Every tool takes the project path as an argument, so KDENLIVE_MCP_PROJECT is a convenience, not a requirement. The variables exist for people who want to set a default project or point at an unusual melt build — nothing breaks if you never touch them.

The one thing you do configure once is the MCP client itself (Claude Desktop, OpenCode, Cursor). That is a five-line JSON block, and it is the same block on all three operating systems.

Does the user have to link the project to something first?

No

No linking step, no registration, no "open project" handshake. Point a tool at a .kdenlive path and it works. The server can create one from nothing with kdenlive_create_project, and it can list a directory of them for you.

What does exist is the bin — Kdenlive's own media shelf. Clips you add land there, and kdenlive_add_clip accepts a bin clip id instead of a file path when you want to reuse the same media on the timeline twice.

Does Kdenlive have to be open?

No — and this matters

Kdenlive does not need to be running. Not for reading, not for editing, not for rendering. Rendering shells out to MLT's melt directly, so a headless box with Kdenlive installed is a fully functional video production machine.

But do not edit the same file from both sides at once. Kdenlive holds the project in memory and rewrites the entire document when you hit save. If you edit the file through the MCP while Kdenlive has it open, then save in Kdenlive, your changes are gone — Kdenlive overwrites the file with its stale in-memory copy. Pick one owner for a given file at a given moment. If you need to hand work back and forth, use the bridge below so a single process stays the source of truth.
Which tools put an HTML file and a plan config together?

None of them — and that is deliberate. The whole design is that the project file is the data. There is no sidecar HTML, no config schema, no manifest to keep in sync with the timeline. A .kdenlive file is self-describing: the profile, the sequences, the tracks, the clips and their effects are all right there in it.

What you get instead is a validator. kdenlive_validate_project reports dangling references, producers defined after the elements that use them, stale cached durations and missing media. Run it after a batch of edits and you get a factual report instead of a guess.

How it is put together

Pure Python, no framework between you and the XML. The layers are small and each one is useful on its own.

ModuleJob
mltxml.pyThe project model. Reads and writes MLT XML, resolves sequences, tracks, clips and the bin, performs frame-accurate playlist edits.
schema.pyMLT's content models, transcribed from the upstream DTD. Catches ordering mistakes that silently break Kdenlive.
validate.pyStructural validation: dangling and forward references, stale durations, missing media, effects without a service name.
_catalog.py407 effects and 53 transitions with their real parameter names. Generated, never hand-edited.
media.pyffprobe wrapper for real durations, frame rates and stream layouts.
render.pyBackground rendering through melt, with progress parsing and cancellation.
bridge.pyHTTP client for reaching a Kdenlive on another machine.
binaries.pyLocates melt, ffprobe and ffmpeg across Linux, macOS, Windows and WSL.

The format rules that bite

These are the details that separate a project Kdenlive opens cleanly from one it chokes on. Every one of them was read out of the upstream source and then confirmed by rendering with MLT 7.41 — not guessed.

RuleWhy it matters
Clip effects live inside the <entry> Not on the producer. The same media can sit on the timeline twice and each instance carries its own effects.
Track effects live inside the track's <tractor> Not on the track's first playlist. Only Kdenlive's internally added audio-mixer filters go on the tractor as well.
Master effects live inside the sequence's <tractor> The sequence tractor is the timeline; the project tractor at the end of the file is just the wrapper pointing at it.
The sequence tractor's element id is its uuid Not a tractorN name. main_bin and the project tractor reference that uuid.
Producers are defined before the elements that use them MLT resolves references in document order. A chain appended at the end of the file is a forward reference and it will not resolve.
Two timecode formats are in play HH:MM:SS.mmm is a millisecond clock value for MLT's in/out. HH:MM:SS:FF is a frame count for Kdenlive's kdenlive:duration. Mixing them silently shifts your timeline by a frame.
out is inclusive A clip's length is out - in + 1, not out - in.
Ids are unique across the whole tree Filters and transitions are nested inside tractors, so an id generator that only scans root children will hand out duplicates.

The tool surface

Thirty-two tools, grouped by what you are trying to do. The design rule: every tool returns facts about the file, never a guess. A tool that reports success without evidence is worse than no tool at all.

GroupTools
Inspect kdenlive_status, kdenlive_project_info, kdenlive_sequences, kdenlive_tracks, kdenlive_clips, kdenlive_bin, kdenlive_effects_on, kdenlive_effects_catalog, kdenlive_validate_project
Build kdenlive_create_project, kdenlive_add_track, kdenlive_remove_track, kdenlive_add_clip, kdenlive_remove_clip, kdenlive_move_clip, kdenlive_trim_clip, kdenlive_split_clip, kdenlive_set_clip_property, kdenlive_set_track_property
Effects kdenlive_add_effect, kdenlive_remove_effect, kdenlive_add_transition, kdenlive_remove_transition

Bridge & paths kdenlive_bridge_status, kdenlive_bridge_projects, kdenlive_bridge_open, kdenlive_bridge_render, kdenlive_path_translate
Positions and durations are frames by default. A timecode string like "00:00:05.000" is accepted anywhere a frame count is, and track, clip and sequence references accept an index, a name or an id. The model should never have to convert between representations by hand.

Install

One command on every platform. uv handles the interpreter, the virtualenv and the entry point.

# anywhere -- macOS, Linux, Windows (PowerShell)
uv tool install kdenlive-mcp

# or from a checkout
uv sync
uv run kdenlive-mcp

Client configuration

Claude Desktop, OpenCode and Cursor all take the same shape — a command, some args, and optionally an environment block:

{
  "mcpServers": {
    "kdenlive": {
      "command": "uv",
      "args": ["tool", "run", "--from", "kdenlive-mcp", "kdenlive-mcp"],
      "env": { "KDENLIVE_MCP_PROJECT": "/home/me/Videos/myproject.kdenlive" }
    }
  }
}

Optional: the renderer

melt ships with Kdenlive. Linux: apt install melt. macOS: brew install mlt. Windows: install Kdenlive and it lands in C:\Program Files\Kdenlive\bin\melt.exe. If it is somewhere odd, point at it with KDENLIVE_MCP_MELT. Portable builds that need MLT_REPOSITORY and friends get them through KDENLIVE_MCP_MELT_ENV.

WSL: the server in Linux, Kdenlive on Windows

This is the configuration the thing was designed around, so it splits cleanly into two halves.

Half one — editing, for free

A project on the Windows drive is reachable from WSL through /mnt/c. Since the MCP edits the file directly, there is no boundary to cross. No bridge, no configuration, no Windows binary involved. 

ls /mnt/c/Users/me/Videos/myproject.kdenlive   # just works

Half two — rendering and the GUI, via the bridge

Those need the machine that actually has Kdenlive on it. The bridge is a tiny stdlib-only HTTP server that runs on the Windows side and hands back a local render or launches the editor. 

# on Windows
python bridge\kdenlive_bridge.py
# Kdenlive bridge listening on http://127.0.0.1:8765

# inside WSL -- the Windows host address
export KDENLIVE_MCP_BRIDGE_URL=http://172.28.224.1:8765

The server probes 127.0.0.1 first, then the WSL gateway, so Windows 11 mirrored networking needs no configuration at all. The same bridge reaches a Kdenlive on a different machine over the network — nothing about it is WSL-specific.

The bridge has no authentication. It binds to 127.0.0.1 by default and it should stay there. Do not expose it to the internet.

What was actually verified

Assertions without artifacts are marketing. Here is what ran, and what came back.

  • 81 of 81 tests pass, including five that render real video through MLT 7.41 and probe the output frame by frame.
  • All eight of Kdenlive's own test projects load through the model — these are unmodified upstream fixtures, used as ground truth.
  • Generated projects satisfy MLT's content models — the same checks the eight upstream fixtures pass, transcribed from MLT's DTD.
  • A full round trip renders correctly. Create project → two clips on two tracks → clip effect → transition → trim → validate → render. Output: 125 frames, 1920×1080, 25 fps, H.264/AAC, 5.013 s. The clip effect is visibly inverted, the second track composites over the first, and the trim lands exactly where it was asked to.
  • Effect scope was verified per scope, not assumed. Clip scope, track scope and sequence scope were each rendered and the pixels checked. A clip effect on the entry, a track effect on the tractor, a master effect on the sequence tractor — all three produce the inverted frame, and a split carries its effects onto both halves.
  • The bridge was exercised end to end, including a render started through the MCP and completed on the bridge machine.
One honest caveat: the render verification ran against MLT 7.41 on Linux. The XML output is platform independent by construction, but the melt invocations on Windows and macOS have not been run on this machine.

Known limits

  • One writer per file at a time. Covered above, and it is the single most likely way to lose work.
  • Round-trip fidelity is not guaranteed for every Kdenlive feature. The model reads and writes the structures it needs and preserves the rest untouched, but obscure features — the timeline's own preview track, some proxy states — are carried along rather than understood.
  • Render progress is parsed from melt's output text. That format has been stable for years, but it is text scraping, not an API.
  • The bridge is unauthenticated. Loopback only.
